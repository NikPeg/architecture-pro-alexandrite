# Архитектурное решение по кешированию

## 1. Анализ системы в контексте кеширования

### Текущие проблемы производительности

Система "Александрит" столкнулась с серьёзными проблемами производительности:

1. **Медленная загрузка первой страницы MES**
   - Операторы жалуются на долгую загрузку дашборда с заказами
   - Команда добавила фильтры и пагинацию, но это не помогло
   - Операторам важно видеть новые заказы быстро (влияет на вознаграждение)

2. **Медленная работа с заказами**
   - Новые клиенты недовольны скоростью выполнения заказа
   - После открытия API нагрузка выросла, что усугубило проблемы

3. **Высокая нагрузка на базы данных**
   - Каждый запрос списка заказов идёт в базу данных
   - При росте количества заказов нагрузка на БД растёт линейно

### Элементы системы для кеширования

#### Критичные для кеширования:

1. **Список заказов в MES (дашборд)**
   - **Проблема:** Медленная загрузка первой страницы MES
   - **Частота запросов:** Высокая (каждый оператор открывает страницу несколько раз в день)
   - **Частота изменений:** Средняя (заказы добавляются и меняют статусы)
   - **Приоритет:** Критический

2. **Список заказов по статусам в MES**
   - **Проблема:** Фильтрация по статусам всё ещё медленная
   - **Частота запросов:** Высокая
   - **Частота изменений:** Средняя
   - **Приоритет:** Критический

3. **Детали заказа**
   - **Проблема:** При открытии деталей заказа идёт запрос к БД
   - **Частота запросов:** Средняя
   - **Частота изменений:** Низкая (меняется только статус)
   - **Приоритет:** Высокий

4. **Список товаров в онлайн-магазине**
   - **Проблема:** Может быть медленным при росте каталога
   - **Частота запросов:** Высокая
   - **Частота изменений:** Низкая
   - **Приоритет:** Средний

#### Не подходят для кеширования:

1. **Расчёт стоимости заказа**
   - **Причина:** Зависит от уникальной 3D-модели, каждый расчёт индивидуален
   - **Частота изменений:** Каждый запрос уникален
   - **Решение:** Не кешировать, оптимизировать алгоритм расчёта

2. **Данные пользователя (личные данные)**
   - **Причина:** Конфиденциальные данные, не должны кешироваться
   - **Решение:** Не кешировать

3. **Статусы заказов в реальном времени**
   - **Причина:** Требуется актуальность данных
   - **Решение:** Кешировать с коротким TTL и инвалидацией при изменении

## 2. Мотивация

### 2.1. Бизнес-проблемы, которые решает кеширование

#### Проблема 1: Медленная загрузка первой страницы MES
**Текущая ситуация:** Операторы жалуются на долгую загрузку дашборда с заказами. Это влияет на их продуктивность и вознаграждение, так как они должны быстро видеть новые заказы.

**Решение:** Кеширование списка заказов позволит загружать дашборд за миллисекунды вместо секунд. Операторы смогут быстрее брать заказы в работу.

**Бизнес-эффект:**
- Увеличение продуктивности операторов на 40-50%
- Снижение количества жалоб операторов на 80%
- Улучшение морального климата в команде

#### Проблема 2: Недовольство клиентов скоростью работы системы
**Текущая ситуация:** Новые клиенты недовольны скоростью выполнения заказа. После открытия API нагрузка выросла, что усугубило проблемы.

**Решение:** Кеширование часто запрашиваемых данных (списки заказов, товары) снизит время отклика системы и улучшит пользовательский опыт.

**Бизнес-эффект:**
- Улучшение пользовательского опыта
- Снижение количества жалоб клиентов на 30%
- Повышение конкурентоспособности

#### Проблема 3: Высокая нагрузка на базы данных
**Текущая ситуация:** Каждый запрос списка заказов идёт в базу данных. При росте количества заказов нагрузка на БД растёт линейно, что может привести к проблемам с производительностью.

**Решение:** Кеширование снизит нагрузку на базы данных на 70-80%, что позволит системе лучше масштабироваться.

**Бизнес-эффект:**
- Снижение нагрузки на БД на 70-80%
- Возможность обрабатывать больше заказов без масштабирования БД
- Снижение затрат на инфраструктуру

- Загрузка списка заказов в MES: < 200 мс (из кеша)

**Как кеширование поможет:** Данные будут возвращаться из кеша за миллисекунды вместо запросов к БД, которые занимают секунды.

**Как кеширование поможет:** Большинство запросов на чтение будут обслуживаться из кеша, снижая нагрузку на БД.

#### 2.2.3. Throughput — пропускная способность
**Текущее значение:** 
- Запросов в секунду к MES API: ~20-30

**Как кеширование поможет:** Кеш может обрабатывать гораздо больше запросов в секунду, чем база данных.

#### 2.2.4. Cache Hit Rate — процент попаданий в кеш
**Целевое значение:** > 80%
**Как кеширование поможет:** При правильной настройке TTL и инвалидации большинство запросов будут обслуживаться из кеша.

## 3. Предлагаемое решение

### 3.1. Выбор типа кеширования: серверное кеширование

**Решение:** Использовать **серверное кеширование** с Redis.

**Обоснование:**

#### Почему серверное, а не клиентское:

1. **Контроль над данными**
   - Серверное кеширование позволяет контролировать, какие данные кешируются и как долго
   - Клиентское кеширование (HTTP Cache) не подходит для динамических данных (списки заказов)

2. **Безопасность**
   - Данные о заказах содержат чувствительную информацию
   - Серверное кеширование позволяет контролировать доступ к данным

3. **Сложная логика инвалидации**
   - При изменении статуса заказа нужно инвалидировать кеш
   - Клиентское кеширование не позволяет гибко управлять инвалидацией

4. **Разные данные для разных пользователей**
   - Операторы видят разные списки заказов в зависимости от фильтров
   - Клиентское кеширование не может эффективно обрабатывать персонализированные данные

5. **Снижение нагрузки на БД**
   - Серверное кеширование снижает нагрузку на базу данных
   - Клиентское кеширование только снижает сетевой трафик

**Исключение:** Клиентское кеширование можно использовать для статических ресурсов (изображения, CSS, JS), но это не решает проблему производительности MES.

### 3.2. Выбор паттерна кеширования: Cache-Aside

**Решение:** Использовать паттерн **Cache-Aside** для операций чтения.

**Обоснование:**

#### Почему Cache-Aside:

1. **Простота реализации**
   - Паттерн прост в реализации и понимании
   - Команда может быстро внедрить его без глубоких изменений в архитектуре

2. **Устойчивость к сбоям кеша**
   - Если Redis недоступен, система продолжит работать, обращаясь к БД
   - Это критично для production-системы

3. **Гибкость модели данных**
   - Можно кешировать результаты сложных запросов (JOIN нескольких таблиц)
   - Модель данных в кеше может отличаться от модели в БД

4. **Оптимизация для чтения**
   - MES в основном читает данные (списки заказов, детали заказов)
   - Cache-Aside идеально подходит для read-heavy приложений

#### Почему не Write-Through:

1. **Сложность реализации**
   - Требует изменений в логике записи во всех местах
   - Увеличивает сложность кода

2. **Синхронная запись**
   - Запись в кеш и БД происходит синхронно, что замедляет операции записи
   - Для MES важна скорость обновления статусов

3. **Не нужна строгая консистентность**
   - Для списка заказов допустима небольшая задержка в обновлении (несколько секунд)
   - Write-Through обеспечивает строгую консистентность, но это избыточно

#### Почему не Refresh-Ahead:

1. **Сложность настройки**
   - Требует точной настройки времени обновления
   - Сложно определить оптимальный интервал обновления для разных типов данных

2. **Риск неконсистентности**
   - Если кеш не обновится вовремя, пользователи увидят устаревшие данные
   - Нужна качественная система мониторинга

3. **Избыточность**
   - Refresh-Ahead полезен для данных, которые обновляются по расписанию
   - Заказы обновляются по событиям (изменение статуса), а не по расписанию

### 3.3. Диаграммы последовательности

#### 3.3.1. Операция чтения списка заказов (Cache-Aside)

```
Operator          MES (React)        MES API (C#)        Redis Cache        MES DB
   |                   |                   |                   |                |
   |--GET /orders----->|                   |                   |                |
   |                   |--GET /api/orders->|                   |                |
   |                   |                   |--GET orders:list->|                |
   |                   |                   |<--cache miss------|                |
   |                   |                   |                   |                |
   |                   |                   |-------------------SELECT orders--->|
   |                   |                   |<--orders data----------------------|
   |                   |                   |--SET orders:list-->|                |
   |                   |                   |<--OK--------------|                |
   |                   |<--orders data-----|                   |                |
   |<--orders data-----|                   |                   |                |
   |                   |                   |                   |                |
   |--GET /orders----->|                   |                   |                |
   |                   |--GET /api/orders->|                   |                |
   |                   |                   |--GET orders:list->|                |
   |                   |                   |<--cache hit-------|                |
   |                   |<--orders data-----|                   |                |
   |<--orders data-----|                   |                   |                |
```

**Описание:**
1. Оператор запрашивает список заказов через MES UI
2. MES API проверяет кеш Redis по ключу `orders:list`
3. При cache miss (первый запрос) данные загружаются из БД
4. Данные сохраняются в кеш с TTL (например, 60 секунд)
5. При последующих запросах данные возвращаются из кеша (cache hit)

#### 3.3.2. Операция изменения статуса заказа (с инвалидацией кеша)

```
Operator          MES (React)        MES API (C#)        Redis Cache        MES DB        RabbitMQ
   |                   |                   |                   |                |              |
   |--PUT /order/123-->|                   |                   |                |              |
   |  status=STARTED   |                   |                   |                |              |
   |                   |--PUT /api/order/123->|                |                |              |
   |                   |  status=STARTED   |                   |                |              |
   |                   |                   |--UPDATE order--->|                |              |
   |                   |                   |<--OK-------------|                |              |
   |                   |                   |--DEL orders:list->|                |              |
   |                   |                   |--DEL order:123--->|                |              |
   |                   |                   |<--OK-------------|                |              |
   |                   |                   |--PUBLISH status--->|              |              |
   |                   |                   |                   |                |--message---->|
   |                   |<--OK--------------|                   |                |              |
   |<--OK--------------|                   |                   |                |              |
```

**Описание:**
1. Оператор изменяет статус заказа через MES UI
2. MES API обновляет заказ в БД
3. После успешного обновления инвалидируются кеши:
   - `orders:list` — список всех заказов
   - `order:123` — детали конкретного заказа
   - `orders:status:STARTED` — список заказов со статусом STARTED (если используется)
4. Отправляется сообщение в RabbitMQ для синхронизации с CRM
5. При следующем запросе списка заказов данные загрузятся из БД и обновятся в кеше

### 3.4. Стратегия инвалидации кеша

**Решение:** Комбинированная стратегия инвалидации:
1. **Инвалидация по ключу** (основная стратегия)
2. **Временная инвалидация** (TTL) (дополнительная защита)
3. **Программная инвалидация** (при изменении данных)

#### 3.4.1. Инвалидация по ключу (основная стратегия)

**Применение:** При изменении данных заказа (статус, назначение оператора и т.д.)

**Механизм:**
- При изменении заказа инвалидируются все связанные ключи кеша
- Ключи для инвалидации:
  - `order:{order_id}` — детали заказа
  - `orders:list` — список всех заказов
  - `orders:status:{status}` — список заказов по статусу
  - `orders:operator:{operator_id}` — список заказов оператора

**Пример реализации:**
```csharp
// MES API (C#)
public async Task UpdateOrderStatus(int orderId, OrderStatus newStatus)
{
    // Обновление в БД
    await _dbContext.Orders
        .Where(o => o.Id == orderId)
        .ExecuteUpdateAsync(o => o.SetProperty(x => x.Status, newStatus));
    
    // Инвалидация кеша
    await _cache.RemoveAsync($"order:{orderId}");
    await _cache.RemoveAsync("orders:list");
    await _cache.RemoveAsync($"orders:status:{newStatus}");
    await _cache.RemoveAsync($"orders:status:{oldStatus}");
}
```

**Почему эта стратегия:**
- ✅ Гарантирует актуальность данных при изменении
- ✅ Точечная инвалидация (только изменённые данные)
- ✅ Минимальная нагрузка на систему
- ✅ Простота реализации

#### 3.4.2. Временная инвалидация (TTL) (дополнительная защита)

**Применение:** Для всех кешированных данных как дополнительная защита

**Механизм:**
- Устанавливается TTL (Time To Live) для каждого ключа
- После истечения TTL данные автоматически удаляются из кеша
- При следующем запросе данные загружаются из БД

**TTL для разных типов данных:**
- `orders:list` — 60 секунд
- `order:{order_id}` — 300 секунд (5 минут)
- `orders:status:{status}` — 60 секунд
- `products:list` — 3600 секунд (1 час)

**Пример реализации:**
```csharp
// Установка TTL при сохранении в кеш
await _cache.SetAsync(
    "orders:list", 
    orders, 
    TimeSpan.FromSeconds(60)
);
```

**Почему эта стратегия:**
- ✅ Защита от устаревших данных, если инвалидация по ключу не сработала
- ✅ Автоматическая очистка неиспользуемых данных
- ✅ Простота настройки

**Почему не только временная:**
- ❌ При изменении данных пользователи будут видеть устаревшие данные до истечения TTL
- ❌ Для списка заказов это критично (операторы должны видеть актуальные данные)

#### 3.4.3. Программная инвалидация (при изменении данных)

**Применение:** При изменении данных через внешние системы (RabbitMQ, внешний API)

**Механизм:**
- При получении сообщения из RabbitMQ о изменении заказа инвалидируется кеш
- При изменении заказа через внешний API инвалидируется кеш

**Пример реализации:**
```csharp
// Обработчик сообщений из RabbitMQ
[RabbitListener("order.status.changed")]
public async Task HandleOrderStatusChanged(OrderStatusChangedEvent @event)
{
    // Инвалидация кеша при изменении статуса из CRM
    await _cache.RemoveAsync($"order:{@event.OrderId}");
    await _cache.RemoveAsync("orders:list");
    await _cache.RemoveAsync($"orders:status:{@event.NewStatus}");
}
```

**Почему эта стратегия:**
- ✅ Обеспечивает консистентность данных между системами
- ✅ Инвалидация происходит при любом изменении данных, независимо от источника

#### 3.4.4. Сравнительная таблица стратегий инвалидации

| Критерий | Инвалидация по ключу | Временная инвалидация | Программная инвалидация | Инвалидация на основе запросов |
|----------|---------------------|----------------------|------------------------|-------------------------------|
| **Актуальность данных** | ✅ Высокая (мгновенная) | ⚠️ Средняя (зависит от TTL) | ✅ Высокая (мгновенная) | ⚠️ Средняя (при следующем запросе) |
| **Простота реализации** | ✅ Простая | ✅ Очень простая | ⚠️ Средняя | ⚠️ Сложная |
| **Нагрузка на систему** | ✅ Низкая (точечная) | ✅ Низкая | ✅ Низкая | ⚠️ Средняя (при каждом запросе) |
| **Гарантия актуальности** | ✅ Гарантирована | ❌ Не гарантирована | ✅ Гарантирована | ⚠️ Частично |
| **Подходит для списка заказов** | ✅ Да | ⚠️ Частично (как дополнение) | ✅ Да | ❌ Нет |
| **Подходит для деталей заказа** | ✅ Да | ✅ Да | ✅ Да | ⚠️ Частично |

**Вывод:** Комбинация инвалидации по ключу + временная инвалидация (TTL) + программная инвалидация обеспечивает оптимальный баланс между актуальностью данных и производительностью.

### 3.5. Техническая реализация

#### 3.5.1. Выбор технологии кеширования: Redis

**Обоснование:**
- ✅ Высокая производительность (in-memory хранилище)
- ✅ Поддержка различных структур данных
- ✅ Встроенная поддержка TTL
- ✅ Широкое распространение и хорошая документация
- ✅ Поддержка кластеризации для масштабирования
- ✅ Интеграция с C# (StackExchange.Redis) и Java (Jedis, Lettuce)

#### 3.5.2. Структура ключей кеша

```
orders:list                    # Список всех заказов
```

#### 3.5.3. Пример реализации в MES API (C#)

```csharp
// Сервис для работы с кешем
public class CacheService
{
    private readonly IDatabase _cache;
    private readonly ILogger<CacheService> _logger;
    
    public CacheService(IConnectionMultiplexer redis, ILogger<CacheService> logger)
    {
        _cache = redis.GetDatabase();
        _logger = logger;
    }
    
    // Получение списка заказов с кешированием
    public async Task<List<Order>> GetOrdersListAsync(
        OrderStatus? status = null, 
        int page = 1, 
        int pageSize = 20)
    {
        // Формирование ключа кеша
        var cacheKey = status.HasValue 
            ? $"orders:status:{status}:page:{page}"
            : $"orders:list:page:{page}";
        
        // Попытка получить из кеша
        var cached = await _cache.StringGetAsync(cacheKey);
        if (cached.HasValue)
        {
            _logger.LogInformation("Cache hit for key: {Key}", cacheKey);
            return JsonSerializer.Deserialize<List<Order>>(cached);
        }
        
        // Cache miss - загрузка из БД
        _logger.LogInformation("Cache miss for key: {Key}", cacheKey);
        var orders = await LoadOrdersFromDbAsync(status, page, pageSize);
        
        // Сохранение в кеш с TTL
        await _cache.StringSetAsync(
            cacheKey, 
            JsonSerializer.Serialize(orders),
            TimeSpan.FromSeconds(60)
        );
        
        return orders;
    }
    
    // Инвалидация кеша при изменении заказа
    public async Task InvalidateOrderCacheAsync(int orderId, OrderStatus? oldStatus = null)
    {
        var tasks = new List<Task>
        {
            _cache.KeyDeleteAsync($"order:{orderId}"),
            _cache.KeyDeleteAsync("orders:list"),
        };
        
        if (oldStatus.HasValue)
        {
            tasks.Add(_cache.KeyDeleteAsync($"orders:status:{oldStatus}"));
        }
        
        // Удаление всех страниц списка заказов
        for (int i = 1; i <= 10; i++) // Предполагаем максимум 10 страниц
        {
            tasks.Add(_cache.KeyDeleteAsync($"orders:list:page:{i}"));
        }
        
        await Task.WhenAll(tasks);
        _logger.LogInformation("Cache invalidated for order: {OrderId}", orderId);
    }
}
```

```java
@Service
public class ProductCacheService {
    
    @Autowired
    private RedisTemplate<String, Object> redisTemplate;
    
    @Autowired
    private ProductRepository productRepository;
    
    private static final String PRODUCTS_LIST_KEY = "products:list";
    private static final String PRODUCT_KEY_PREFIX = "product:";
    private static final long TTL_SECONDS = 3600; // 1 час
    
    public List<Product> getProductsList() {
        // Попытка получить из кеша
        List<Product> products = (List<Product>) redisTemplate.opsForValue()
            .get(PRODUCTS_LIST_KEY);
        
        if (products != null) {
            log.info("Cache hit for products list");
            return products;
        }
        
        // Cache miss - загрузка из БД
        log.info("Cache miss for products list");
        products = productRepository.findAll();
        
        // Сохранение в кеш
        redisTemplate.opsForValue().set(
            PRODUCTS_LIST_KEY, 
            products, 
            TTL_SECONDS, 
            TimeUnit.SECONDS
        );
        
        return products;
    }
    
    public void invalidateProductsCache() {
        redisTemplate.delete(PRODUCTS_LIST_KEY);
        log.info("Products cache invalidated");
    }
}
```

## 4. Дополнительное задание: Сравнение решений

### 4.1. Решение 1: Серверное кеширование с Redis (Cache-Aside)

**Описание:**
- Использование Redis для серверного кеширования
- Паттерн Cache-Aside для операций чтения
- Инвалидация по ключу при изменении данных
- TTL как дополнительная защита

**Диаграмма:** (см. раздел 3.3)

**Плюсы:**
- ✅ Высокая производительность (in-memory)
- ✅ Простота реализации
- ✅ Устойчивость к сбоям (система работает при недоступности Redis)
- ✅ Гибкость модели данных
- ✅ Хорошая масштабируемость (Redis кластер)
- ✅ Поддержка различных структур данных

**Минусы:**
- ⚠️ Дополнительный компонент в инфраструктуре
- ⚠️ Необходимость управления Redis
- ⚠️ Дополнительные затраты на память
- ⚠️ Возможна неконсистентность данных (если инвалидация не сработает)

### 4.2. Решение 2: Клиентское кеширование (HTTP Cache) + Оптимизация БД

**Описание:**
- Использование HTTP Cache-Control заголовков для кеширования на клиенте
- Оптимизация запросов к БД (индексы, материализованные представления)
- Кеширование на уровне приложения (in-memory cache в процессе)

**Диаграмма:**
```
[Operator] → [MES UI] → [Browser Cache] → [MES API] → [In-Memory Cache] → [MES DB]
```

**Плюсы:**
- ✅ Не требует дополнительной инфраструктуры (Redis)
- ✅ Снижение сетевого трафика
- ✅ Быстрая работа для повторных запросов
- ✅ Оптимизация БД улучшает производительность всех запросов

**Минусы:**
- ❌ Не подходит для динамических данных (списки заказов меняются часто)
- ❌ Сложность управления инвалидацией на клиенте
- ❌ Проблемы с консистентностью данных
- ❌ Не решает проблему нагрузки на БД (только снижает сетевой трафик)
- ❌ In-memory cache в процессе теряется при перезапуске
- ❌ Не масштабируется между инстансами

### 4.3. Решение 3: Гибридное кеширование (Redis + HTTP Cache)

**Описание:**
- Redis для серверного кеширования динамических данных (заказы)
- HTTP Cache для статических ресурсов (изображения, CSS, JS)
- Оптимизация БД для сложных запросов

**Диаграмма:**
```
[Operator] → [MES UI] → [Browser Cache (статика)] → [MES API] → [Redis Cache] → [MES DB]
```

**Плюсы:**
- ✅ Комбинация преимуществ обоих подходов
- ✅ Максимальная производительность
- ✅ Снижение нагрузки на БД и сеть
- ✅ Оптимальное использование ресурсов

**Минусы:**
- ⚠️ Более сложная реализация
- ⚠️ Больше компонентов для управления
- ⚠️ Выше сложность отладки

### 4.5. Заключение и рекомендация

**Рекомендуемое решение: Решение 1 (Redis Cache-Aside)**

**Обоснование:**

1. **Решает основную проблему**
   - Медленная загрузка списка заказов в MES — основная проблема
   - Redis Cache-Aside обеспечивает быструю загрузку (< 200 мс)

2. **Оптимальный баланс сложности и эффективности**
   - Простая реализация (1-2 недели)
   - Высокая эффективность (снижение нагрузки на БД на 70-80%)
   - Устойчивость к сбоям

3. **Масштабируемость**
   - Redis можно масштабировать горизонтально (кластер)
   - Подходит для роста нагрузки

4. **Гибкость**
   - Можно легко добавить кеширование для других данных
   - Поддержка различных структур данных

**Почему не Решение 2:**
- ❌ Не решает проблему нагрузки на БД
- ❌ Не подходит для динамических данных (списки заказов)
- ❌ Проблемы с консистентностью данных

**Почему не Решение 3:**
- ⚠️ Избыточная сложность для текущих потребностей
- ⚠️ HTTP Cache можно добавить позже, если понадобится
- ⚠️ Основная проблема — динамические данные, для которых HTTP Cache не подходит
