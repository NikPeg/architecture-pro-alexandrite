# Архитектурное решение по логированию

## 1. Анализ системы в контексте логирования

### Текущая архитектура и точки сбора логов

Система "Александрит" представляет собой распределённую микросервисную архитектуру с несколькими критическими компонентами, которые требуют логирования:

#### Системы, требующие сбора логов:

1. **Онлайн-магазин (Vue + Shop API)**
   - Логирование действий пользователей
   - Логирование создания заказов
   - Логирование загрузки 3D-файлов
   - Ошибки на фронтенде и бэкенде

2. **Shop API (Java Spring Boot)**
   - HTTP-запросы и ответы
   - Операции с базой данных
   - Интеграция с S3 Storage
   - Отправка сообщений в RabbitMQ

3. **Shop DB (PostgreSQL)**
   - Медленные запросы
   - Ошибки подключения
   - Блокировки и deadlocks

4. **CRM (Vue + CRM API)**
   - Действия продавцов
   - Изменения статусов заказов
   - Работа с заказами

5. **CRM API (Java Spring Boot)**
   - Обработка заказов
   - Интеграция с RabbitMQ
   - Работа с 3D Files Storage

6. **3D Files Storage (S3)**
   - Логи доступа к файлам
   - Ошибки загрузки/скачивания
   - Использование хранилища

7. **Messages Queue (RabbitMQ)**
   - Сообщения в очередях
   - Ошибки обработки сообщений
   - Потеря сообщений
   - Длительность обработки сообщений

8. **MES API (C#)**
   - Расчёт стоимости заказов
   - Распределение заказов между операторами
   - Изменения статусов заказов
   - Долгие операции (2-30 минут)

9. **MES (React)**
   - Действия операторов
   - Загрузка списка заказов
   - Фильтрация и пагинация

10. **MES DB (PostgreSQL)**
    - Медленные запросы
    - Ошибки подключения
    - Операции с заказами

11. **External API (MES API для внешних продавцов)**
    - Запросы от внешних продавцов
    - Расчёт стоимости через API
    - Ошибки интеграции

### Схема архитектуры с точками сбора логов

**Примечание:** На C4-диаграмме должны быть отмечены все системы, из которых требуется сбор логов. Системы, требующие логирования, выделяются специальным маркером или цветом.

**Системы для сбора логов (отмечены на схеме):**
- ✅ Shop API
- ✅ Shop DB
- ✅ CRM API
- ✅ 3D Files Storage (S3)
- ✅ RabbitMQ
- ✅ MES API
- ✅ MES DB
- ✅ External API endpoints

**Системы с опциональным логированием:**
- ⚠️ Фронтенд-приложения (Vue, React) — только критичные ошибки
- ⚠️ Инфраструктурные компоненты (EC2, сеть)

## 2. Список необходимых логов уровня INFO

### 2.1. Shop API (Java Spring Boot)

#### Создание и управление заказами:
- **Создание заказа**
  - Время: timestamp
  - Идентификатор покупателя: user_id
  - Номер заказа: order_id
  - Источник заказа: source (internet_shop, external_api)
  - Статус: status (INITIATED)
  - IP-адрес клиента: client_ip
  - User-Agent: user_agent

- **Загрузка 3D-файла**
  - Время: timestamp
  - Номер заказа: order_id
  - Идентификатор файла: file_id
  - Размер файла: file_size (bytes)
  - Тип файла: file_type
  - Результат загрузки: upload_status (success, failed)
  - URL в S3: s3_url

- **Изменение статуса заказа**
  - Время: timestamp
  - Номер заказа: order_id
  - Старый статус: old_status
  - Новый статус: new_status
  - Инициатор изменения: changed_by (system, user_id)

#### Интеграции:
- **Отправка сообщения в RabbitMQ**
  - Время: timestamp
  - Номер заказа: order_id
  - Очередь: queue_name
  - Тип сообщения: message_type
  - Результат: result (sent, failed)

- **Запрос к базе данных**
  - Время: timestamp
  - Тип операции: operation_type (SELECT, INSERT, UPDATE, DELETE)
  - Таблица: table_name
  - Длительность: duration_ms
  - Номер заказа (если применимо): order_id

### 2.2. CRM API (Java Spring Boot)

#### Управление заказами:
- **Получение заказа из очереди**
  - Время: timestamp

- **Изменение статуса заказа**

- **Подтверждение производства**

  - Продавец: seller_id

#### Работа с файлами:

  - Время: timestamp

  - Пользователь: user_id

## 3. Другие уровни логирования

### 3.1. Уровень ERROR

**Использование:** Критические ошибки, которые требуют немедленного внимания.

**Примеры:**
- Ошибки при создании заказа (не удалось сохранить в БД)
- Ошибки при расчёте стоимости (исключение в MES API)
- Потеря сообщений в RabbitMQ
- Ошибки подключения к базе данных
- Ошибки загрузки файлов в S3
- Ошибки валидации данных
- Ошибки аутентификации/авторизации

**Формат лога:**
```json
{
  "timestamp": "2024-01-15T10:30:00Z",
  "level": "ERROR",
  "service": "shop-api",
  "order_id": "12345",
  "error_type": "database_connection_error",
  "error_message": "Connection to database failed",
  "stack_trace": "...",
  "context": {
    "operation": "create_order",
    "user_id": "user-123"
  }
}
```

### 3.2. Уровень WARN

**Использование:** Предупреждения о потенциальных проблемах или нестандартных ситуациях.

**Примеры:**
- Медленный запрос к базе данных (> 1 секунды)
- Повторная попытка обработки сообщения из очереди
- Заказ не менял статус более 1 часа
- Расчёт стоимости занимает более 30 минут
- Необычно большое количество запросов от одного IP
- Недостаточно места в хранилище S3
- Высокая загрузка очереди RabbitMQ

**Формат лога:**
```json
{
  "timestamp": "2024-01-15T10:30:00Z",
  "level": "WARN",
  "service": "mes-api",
  "order_id": "12345",
  "warning_type": "slow_calculation",
  "message": "Price calculation takes longer than expected",
  "duration_ms": 1800000,
  "expected_duration_ms": 120000
}
```

### 3.3. Уровень DEBUG

**Использование:** Детальная информация для отладки. Используется только в dev-окружении.

**Примеры:**
- Детали выполнения SQL-запроса
- Параметры вызова метода
- Промежуточные значения в расчётах
- Детали обработки сообщений из очереди
- Трассировка выполнения алгоритма

**Формат лога:**
```json
{
  "timestamp": "2024-01-15T10:30:00Z",
  "level": "DEBUG",
  "service": "shop-api",
  "method": "createOrder",
  "parameters": {
    "user_id": "user-123",
    "items": [...]
  },
  "intermediate_values": {
    "total_price": 15000,
    "discount": 0
  }
}
```

**Важно:** Уровень DEBUG не должен использоваться в production-окружении из-за большого объёма данных и потенциального влияния на производительность.

### 3.4. Уровень FATAL

**Использование:** Критические ошибки, которые приводят к остановке сервиса или невозможности продолжения работы.

**Примеры:**
- Не удалось подключиться к базе данных при старте приложения
- Не удалось подключиться к RabbitMQ при старте
- Критическая ошибка в конфигурации
- Недостаточно ресурсов для работы сервиса

**Формат лога:**
```json
{
  "timestamp": "2024-01-15T10:30:00Z",
  "level": "FATAL",
  "service": "shop-api",
  "error_type": "database_connection_failed",
  "error_message": "Cannot connect to database. Service cannot start.",
  "stack_trace": "...",
  "action_required": "immediate_attention"
}
```

### 3.5. Уровень TRACE

**Использование:** Максимально детальная информация. Используется только в dev-окружении для отладки конкретных проблем.

**Примеры:**
- Каждый шаг выполнения алгоритма
- Детали работы с сетью
- Детали работы с файловой системой
- Детали сериализации/десериализации

**Важно:** Уровень TRACE не должен использоваться в production-окружении.

## 4. Мотивация

### 4.1. Бизнес-проблемы, которые решает логирование

#### Проблема 1: Разбор ошибок и нестандартных ситуаций со слов клиента
**Текущая ситуация:** Клиенты сообщают о проблемах, но разработчикам и поддержке требуется много времени, чтобы понять, что произошло на стороне сервиса.

**Решение:** Централизованное логирование позволяет быстро найти все логи, связанные с конкретным заказом или пользователем, по order_id или user_id. Это сокращает время диагностики с часов до минут.

**Бизнес-эффект:**
- Сокращение времени на разбор проблем с 2-4 часов до 15-30 минут
- Снижение нагрузки на службу поддержки на 40%
- Повышение удовлетворённости клиентов

#### Проблема 2: Невозможность понять причину потери заказов
**Текущая ситуация:** После открытия API для внешних продавцов участились случаи потери заказов. Невозможно понять, на каком этапе заказ был потерян.

**Решение:** Логирование всех операций с заказами позволяет отследить полный жизненный цикл заказа и выявить, где именно произошла потеря.

**Бизнес-эффект:**
- Снижение количества потерянных заказов на 80%
- Восстановление потерянных заказов
- Сохранение крупных контрактов

#### Проблема 3: Медленная загрузка первой страницы MES
**Текущая ситуация:** Операторы жалуются на долгую загрузку первой страницы MES с дашбордом заказов. Команда добавила фильтры и пагинацию, но это не помогло.

**Решение:** Логирование медленных запросов к базе данных и анализ логов позволят выявить узкие места и оптимизировать запросы.

**Бизнес-эффект:**
- Улучшение производительности MES на 50%
- Повышение продуктивности операторов
- Снижение количества жалоб операторов

#### Проблема 4: Невозможность проактивно обнаруживать проблемы
**Текущая ситуация:** Проблемы обнаруживаются только после жалоб клиентов или операторов.

**Решение:** Анализ логов в реальном времени и алертинг позволяют обнаруживать проблемы до того, как они повлияют на пользователей.

**Бизнес-эффект:**
- Снижение количества инцидентов на 50%
- Предотвращение потери контрактов
- Повышение надёжности системы

### 4.2. Технические метрики, на которые повлияет логирование

#### 4.2.1. Mean Time To Detect (MTTD) — среднее время обнаружения проблемы
**Текущее значение:** ~2-4 часа (по жалобам клиентов)
**Целевое значение:** < 5 минут
**Как логирование поможет:** Автоматический анализ логов и алертинг при обнаружении ошибок или аномалий

#### 4.2.2. Mean Time To Resolve (MTTR) — среднее время решения проблемы
**Текущее значение:** ~4-8 часов
**Целевое значение:** < 30 минут
**Как логирование поможет:** Быстрый поиск всех логов, связанных с проблемой, по order_id, user_id или trace_id. Понимание полного контекста проблемы.

#### 4.2.3. Error Rate — процент ошибок
**Текущее значение:** Неизвестно (нет данных)
**Целевое значение:** < 0.1%
**Как логирование поможет:** Подсчёт ошибок уровня ERROR из логов, анализ трендов, выявление проблемных мест

#### 4.2.4. P95 Latency — 95-й процентиль задержки
**Текущее значение:** Неизвестно
**Целевое значение:** < 1 секунда для большинства операций
**Как логирование поможет:** Анализ логов с временными метками для измерения latency операций, выявление медленных запросов

#### 4.2.5. System Availability — доступность системы
**Текущее значение:** Неизвестно
**Целевое значение:** 99.9%
**Как логирование поможет:** Отслеживание доступности через логи health check endpoints, анализ причин недоступности

### 4.3. Бизнес-метрики, на которые повлияет логирование

#### 4.3.1. Customer Satisfaction Score (CSAT)
**Текущее значение:** Снижается из-за проблем с заказами
**Целевое значение:** Увеличение на 20%
**Как логирование поможет:** Быстрое решение проблем до того, как они повлияют на клиентов. Проактивное обнаружение и устранение проблем.

#### 4.3.2. Order Completion Rate — процент завершённых заказов
**Текущее значение:** Неизвестно (есть потерянные заказы)
**Целевое значение:** 99.9%
**Как логирование поможет:** Отслеживание каждого заказа через логи, выявление и восстановление потерянных заказов

#### 4.3.3. Support Ticket Volume — количество обращений в поддержку
**Текущее значение:** Растёт из-за проблем с заказами
**Целевое значение:** Снижение на 40%
**Как логирование поможет:** Решение проблем до обращения клиентов, быстрая диагностика при обращении

#### 4.3.4. Cost of Incidents — стоимость инцидентов
**Текущее значение:** Высокая из-за потери контрактов
**Целевое значение:** Снижение на 50%
**Как логирование поможет:** Предотвращение инцидентов через проактивное обнаружение проблем, быстрое устранение проблем

#### 4.3.5. Operator Productivity — продуктивность операторов
**Текущее значение:** Снижается из-за медленной работы MES
**Целевое значение:** Увеличение на 30%
**Как логирование поможет:** Оптимизация производительности MES через анализ логов медленных запросов, улучшение времени загрузки страниц

## 5. Приоритеты внедрения логирования

Команда не сможет реализовать единовременно логирование и трейсинг всех выделенных систем. Необходимо определить приоритеты внедрения.

### 5.1. Критический приоритет (внедрение в первую очередь)

#### Shop API и CRM API
**Причина:**
- Это основные точки входа для создания и обработки заказов
- Большинство проблем с заказами связано с этими сервисами
- Логирование здесь даст максимальный эффект для диагностики проблем

**Что логировать:**
- Все операции с заказами (создание, изменение статуса)
- Интеграции с RabbitMQ
- Операции с базой данных
- Ошибки всех уровней

**Срок внедрения:** 1-2 недели

#### MES API
**Причина:**
- Критичный сервис для расчёта стоимости заказов
- Долгие операции (2-30 минут) требуют логирования для отслеживания прогресса
- Проблемы здесь напрямую влияют на бизнес

**Что логировать:**
- Расчёт стоимости заказов (начало, завершение, ошибки)
- Изменения статусов заказов
- Операции с операторами
- Внешние API запросы

**Срок внедрения:** 1-2 недели

#### RabbitMQ
**Причина:**
- Критичная интеграция между сервисами
- Потеря сообщений приводит к потере заказов
- Необходимо отслеживать все сообщения для диагностики проблем

**Что логировать:**
- Получение и отправка сообщений
- Ошибки обработки сообщений
- Длительность обработки сообщений
- Потеря сообщений

**Срок внедрения:** 1 неделя

### 5.2. Высокий приоритет (внедрение во вторую очередь)

#### Базы данных (Shop DB, MES DB)
**Причина:**
- Медленные запросы влияют на производительность всей системы
- Проблемы с базой данных критичны для работы системы
- Необходимо для оптимизации производительности MES

**Что логировать:**
- Медленные запросы (> 1 секунды)
- Ошибки подключения
- Deadlocks
- Операции с заказами

**Срок внедрения:** 1 неделя

#### 3D Files Storage (S3)
**Причина:**
- Проблемы с загрузкой файлов влияют на создание заказов
- Необходимо отслеживать использование хранилища

**Что логировать:**
- Загрузка и скачивание файлов
- Ошибки доступа к файлам
- Использование хранилища

**Срок внедрения:** 3-5 дней

### 5.3. Средний приоритет (внедрение в третью очередь)

#### Фронтенд-приложения (Vue, React)
**Причина:**
- Меньше критично для диагностики проблем на бэкенде
- Достаточно логировать только критические ошибки

**Что логировать:**
- Критические ошибки (FATAL, ERROR)
- Ошибки загрузки данных
- Проблемы с аутентификацией

**Срок внедрения:** 3-5 дней

#### Инфраструктурные компоненты
**Причина:**
- Менее критично для диагностики бизнес-проблем
- Можно использовать системные логи

**Что логировать:**
- Системные ошибки
- Проблемы с ресурсами

**Срок внедрения:** 3-5 дней

## 7. Политика безопасности

### 7.1. Работа с чувствительными данными

#### Маскирование персональных данных (PII)

**Проблема:** Логи могут содержать персональные данные пользователей, платежную информацию и другую чувствительную информацию.

**Решение:**
- Не логировать пароли, токены, номера карт, CVV-коды
- Маскировать email-адреса (например, `u***@example.com`)
- Маскировать номера телефонов (например, `+7***1234`)
- Использовать только идентификаторы вместо полных данных пользователей

**Реализация в Logstash:**
```ruby
filter {
  # Маскирование email
  if [parsed][email] {
    mutate {
      replace => { 
        "[parsed][email]" => "%{[parsed][email]}" =~ /^(.{1}).*(@.*)$/ ? "${1}***${2}" : "***"
      }
    }
  }
  
  # Удаление чувствительных полей
  mutate {
    remove_field => [ 
      "parsed.password",
      "parsed.token",
      "parsed.card_number",
      "parsed.cvv"
    ]
  }
}
```

- Использовать TLS для соединений между Filebeat и Logstash

## 8. Политика хранения логов

### 8.1. Индексы по системам

**Структура индексов:**
- `logs-shop-api-YYYY.MM.DD` — логи Shop API
- `logs-crm-api-YYYY.MM.DD` — логи CRM API
- `logs-mes-api-YYYY.MM.DD` — логи MES API
- `logs-rabbitmq-YYYY.MM.DD` — логи RabbitMQ
- `logs-postgresql-YYYY.MM.DD` — логи баз данных
- `logs-s3-YYYY.MM.DD` — логи S3 Storage

**Преимущества:**
- Легко найти логи конкретной системы
- Удобно управлять retention policy для разных систем
- Оптимизация производительности поиска

### 8.2. Сроки хранения

#### Критичные логи (ERROR, FATAL):
- **Срок хранения:** 90 дней
- **Причина:** Необходимы для анализа инцидентов и трендов ошибок
- **Объём:** ~10-20 GB в день

#### Обычные логи (INFO, WARN):
- **Срок хранения:** 30 дней
- **Причина:** Достаточно для диагностики недавних проблем
- **Объём:** ~50-100 GB в день

#### Логи уровня DEBUG:
- **Срок хранения:** 7 дней (только в dev-окружении)
- **Причина:** Большой объём данных, используются только для отладки
- **Объём:** ~200-500 GB в день (только в dev)

#### Логи безопасности (аудит, аутентификация):
- **Срок хранения:** 365 дней
- **Причина:** Требования безопасности и соответствия
- **Объём:** ~5-10 GB в день

### 8.3. Размер индексов

#### Оценка объёма данных:

**На один заказ:**
- Shop API: ~10-20 логов
- CRM API: ~5-10 логов
- MES API: ~5-15 логов (включая расчёт стоимости)
- RabbitMQ: ~5-10 логов
- Базы данных: ~20-30 логов (медленные запросы)

**Итого на заказ:** ~45-85 логов

**При 1000 заказов в день:**
- Логов в день: ~45,000 - 85,000
- Размер лога: ~1-2 KB
- **Общий объём в день:** ~45-170 MB

**При 10,000 заказов в день (после открытия API):**
- Логов в день: ~450,000 - 850,000
- **Общий объём в день:** ~450 MB - 1.7 GB

**С учётом всех систем:**
- **Общий объём логов в день:** ~5-10 GB
- **Общий объём логов за 30 дней:** ~150-300 GB
- **Общий объём логов за 90 дней (ERROR):** ~450-900 GB

**Проблема:** Резкий рост количества запросов может указывать на DDoS-атаку.

        "ip_count": {
          "terms": {
            "field": "client_ip",

def create_ticket_for_stuck_order(order_id, logs):

        "labels": ["order", "stuck", "logging"]
    }
    
    response = requests.post(
        "https://tracker.company.com/api/v2/issues",
        json=ticket_data,
        headers={"Authorization": "OAuth ..."}
    )
    return response.json()

def monitor_stuck_orders():
    """Мониторинг застрявших заказов"""
    es = Elasticsearch(['elasticsearch:9200'])
    
    # Поиск заказов, которые не меняли статус более 1 часа
    query = {
        "query": {
            "bool": {
                "must": [
                    {
                        "range": {
                            "@timestamp": {
                                "gte": "now-1h"
                            }
                        }
                    },
                    {
                        "term": {
                            "level": "INFO"
                        }
                    },

                        }
                    }

            }

                    "size": 100
                },

                        "max": {
                            "field": "@timestamp"
                        }
                    }
                }
            }
        }
    }
    
    response = es.search(index="logs-*", body=query)
    
    for bucket in response['aggregations']['stuck_orders']['buckets']:
        order_id = bucket['key']
        last_change = bucket['last_status_change']['value_as_string']
        
        # Если последнее изменение было более 1 часа назад

## 10. Дополнительное задание: Критерии выбора технологии

### 10.1. Критерии выбора

#### 1. Лицензия и стоимость

**ELK Stack (Elasticsearch):**
- **Лицензия:** Elastic License (не полностью open source с версии 7.11+)
- **Стоимость:** Бесплатно для базовых функций, платно для расширенных (Security, Alerting, ML)
- **Плюсы:** Широкое сообщество, много документации
- **Минусы:** Ограничения в бесплатной версии, необходимость платной лицензии для production-ready функций

**OpenSearch:**
- **Лицензия:** Apache License 2.0 (полностью open source)
- **Стоимость:** Полностью бесплатно
- **Плюсы:** Полностью open source, форк Elasticsearch с открытой лицензией
- **Минусы:** Меньше функций, чем в коммерческой версии Elasticsearch, меньше сообщества

**Splunk:**
- **Лицензия:** Проприетарная
- **Стоимость:** Очень дорого (по объёму данных)
- **Плюсы:** Мощные возможности анализа, корпоративная поддержка
- **Минусы:** Высокая стоимость, сложная настройка

**Loki (Grafana):**
- **Лицензия:** Apache License 2.0
- **Стоимость:** Бесплатно
- **Плюсы:** Легковесный, интегрируется с Grafana
- **Минусы:** Меньше функций, чем ELK, менее зрелый продукт

**Выбор для "Александрита":** OpenSearch или ELK Stack (бесплатная версия)
- **Обоснование:** Нужна open source лицензия, достаточный функционал для начала

#### 2. Производительность и масштабируемость

**ELK Stack:**
- **Производительность:** Высокая, оптимизирована для больших объёмов данных
- **Масштабируемость:** Отлично масштабируется горизонтально
- **Плюсы:** Поддержка кластеризации, шардирования
- **Минусы:** Требует много ресурсов (память, CPU)

**OpenSearch:**
- **Производительность:** Сопоставима с Elasticsearch
- **Масштабируемость:** Хорошая, аналогична Elasticsearch
- **Плюсы:** Те же возможности масштабирования
- **Минусы:** Те же требования к ресурсам

**Splunk:**
- **Производительность:** Очень высокая
- **Масштабируемость:** Отличная, но дорогая
- **Плюсы:** Оптимизирована для больших объёмов
- **Минусы:** Высокая стоимость масштабирования

**Loki:**
- **Производительность:** Хорошая для небольших объёмов
- **Масштабируемость:** Ограниченная
- **Плюсы:** Меньше ресурсов, чем ELK
- **Минусы:** Может не справиться с очень большими объёмами

**Выбор для "Александрита":** ELK Stack или OpenSearch
- **Обоснование:** Нужна хорошая масштабируемость для роста нагрузки

#### 3. Простота внедрения и настройки

**ELK Stack:**
- **Простота:** Средняя, требует настройки нескольких компонентов
- **Плюсы:** Много документации, примеров, готовых решений
- **Минусы:** Сложная начальная настройка, требует понимания всех компонентов

**OpenSearch:**
- **Простота:** Средняя, аналогична Elasticsearch
- **Плюсы:** Те же возможности настройки

**Splunk:**
- **Простота:** Сложная, требует обучения

- **Минусы:** Сложная настройка, требует экспертизы

**Loki:**
- **Простота:** Простая, легковесная настройка
- **Плюсы:** Быстрый старт, простая конфигурация
- **Минусы:** Меньше функций

**ELK Stack:**

- **Плюсы:** Отличная интеграция с Grafana (если используется)

## 11. Заключение

Внедрение централизованного логирования в систему "Александрит" критически важно для решения проблем с диагностикой ошибок и нестандартных ситуаций. Логирование позволит:

- Быстро находить и диагностировать проблемы
- Отслеживать полный жизненный цикл заказов
- Проактивно обнаруживать проблемы до жалоб клиентов
- Оптимизировать производительность системы
- Снизить нагрузку на службу поддержки
- Повысить удовлетворённость клиентов

Решение на основе ELK Stack является стандартным, масштабируемым и поддерживаемым, что делает его оптимальным выбором для компании. Поэтапное внедрение позволит команде постепенно освоить инструменты и начать получать пользу от логирования уже на ранних этапах.
