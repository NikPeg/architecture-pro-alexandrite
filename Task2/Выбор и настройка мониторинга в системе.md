# Выбор и настройка мониторинга в системе

## 1. Мотивация

### Текущая ситуация

Компания "Александрит" столкнулась с серьёзными проблемами после открытия API для внешних продавцов:
- Резкий рост количества заказов привёл к увеличению жалоб клиентов
- Потеря крупных контрактов из-за проблем с обработкой заказов
- Невозможность быстро диагностировать причины проблем
- Долгая загрузка первой страницы MES, что влияет на продуктивность операторов

### Проблемы без мониторинга

**Отсутствие видимости системы:**
- Невозможно понять, где именно происходит сбой или задержка
- Проблемы обнаруживаются только после жалоб клиентов
- Нет данных для принятия обоснованных решений по оптимизации

**Экономические потери:**
- Потеря контрактов из-за недоступности системы
- Недовольство клиентов B2C и B2B
- Снижение продуктивности операторов из-за медленной работы MES
- Задержки в разработке из-за невозможности быстро найти причину проблем

**Технические риски:**
- Невозможность прогнозировать нагрузку
- Отсутствие данных для масштабирования
- Нет понимания узких мест в системе
- Сложность диагностики проблем в распределённой системе

### Что даст мониторинг компании

**Для бизнеса:**
- **Предотвращение потери контрактов** — раннее обнаружение проблем до того, как они повлияют на клиентов
- **Повышение удовлетворённости клиентов** — быстрая реакция на проблемы
- **Обоснованные решения по масштабированию** — данные для принятия решений о расширении инфраструктуры
- **Снижение времени простоя** — быстрое обнаружение и устранение проблем

**Для технической команды:**
- **Быстрая диагностика проблем** — понимание, где именно произошёл сбой
- **Проактивное решение проблем** — обнаружение проблем до жалоб пользователей
- **Данные для оптимизации** — понимание узких мест в системе
- **Улучшение процесса разработки** — возможность отслеживать влияние изменений

**Метрики успеха:**
- Время обнаружения проблемы: с "по жалобам клиентов" до < 5 минут
- Время диагностики проблемы: с "несколько часов" до < 30 минут
- Снижение количества инцидентов: на 50% за счёт проактивного обнаружения
- Снижение времени простоя: на 70% за счёт быстрой реакции

## 2. Выбор подхода к мониторингу

### Анализ подходов

Для системы "Александрит" с её микросервисной архитектурой и различными типами компонентов (веб-сервисы, базы данных, очереди) необходимо использовать комбинацию подходов.

### Выбранные подходы

#### 2.1. RED-метод для веб-сервисов и API

**Применение:**
- Shop API
- CRM API
- MES API

**Обоснование:**
RED-метод (Rate, Errors, Duration) идеально подходит для мониторинга веб-сервисов и API, так как:
- Фокусируется на метриках, важных для конечных пользователей
- Позволяет быстро выявить проблемы с производительностью
- Подходит для распределённых систем с множеством запросов
- Метрики легко интерпретировать и визуализировать

**Метрики RED:**
- **Rate (Requests Rate)** — количество запросов в секунду
- **Errors** — количество ошибок в секунду
- **Duration** — время выполнения запросов

#### 2.2. USE-метод для инфраструктурных компонентов

**Применение:**
- Серверы приложений (EC2 инстансы)
- Базы данных (PostgreSQL)
- Очереди сообщений (RabbitMQ)

**Обоснование:**
USE-метод (Utilization, Saturation, Errors) подходит для мониторинга ресурсов, так как:
- Позволяет выявить узкие места на уровне ресурсов
- Помогает понять, когда нужно масштабировать инфраструктуру
- Эффективен для серверов, баз данных и других ресурсов

**Метрики USE:**
- **Utilization** — процент использования ресурса (CPU, память, диск)
- **Saturation** — объём работы, которую ресурс не может выполнить (очереди, задержки)
- **Errors** — количество ошибок

#### 2.3. Четыре золотых сигнала для критических сервисов

**Применение:**
- MES API (расчёт стоимости)
- Интеграция через RabbitMQ

**Обоснование:**
Четыре золотых сигнала (Latency, Traffic, Errors, Saturation) дополняют RED и USE, давая более полную картину для критических компонентов:
- **Latency** — задержка запросов (критично для расчёта стоимости)
- **Traffic** — трафик (количество запросов)
- **Errors** — ошибки
- **Saturation** — насыщенность системы

### Комбинированный подход

Для разных компонентов системы используются разные подходы:

| Компонент | Подход | Причина |
|-----------|--------|---------|
| Shop API, CRM API, MES API | RED | Веб-сервисы, важны метрики для пользователей |
| Серверы приложений | USE | Ресурсы, нужно отслеживать утилизацию |
| Базы данных | USE + Четыре золотых сигнала | Критичные компоненты, нужна полная картина |
| RabbitMQ | USE + Четыре золотых сигнала | Критичная интеграция, нужно отслеживать очереди |
| S3 Storage | USE | Ресурс хранения, важно отслеживать использование |

## 3. Описание метрик

### 3.1. Метрики RabbitMQ

#### Number of dead-letter-exchange letters in RabbitMQ
**Зачем нужна:** 
- Обнаружение сообщений, которые не удалось обработать
- Индикатор проблем в обработке заказов
- Критично для предотвращения потери заказов

**Ярлыки:**
- `queue` — название очереди (например, "order.created", "status.updated")
- `exchange` — название exchange
- `reason` — причина попадания в DLX (timeout, reject, error)

**Пороговые значения:**
- Warning: > 0 сообщений в час
- Critical: > 10 сообщений в час

#### Number of message in flight in RabbitMQ
**Зачем нужна:**
- Понимание текущей нагрузки на систему обработки сообщений
- Индикатор насыщенности системы
- Помогает выявить узкие места в обработке

**Ярлыки:**
- `queue` — название очереди
- `consumer` — потребитель сообщений
- `priority` — приоритет сообщения (если используется)

**Пороговые значения:**
- Warning: > 1000 сообщений
- Critical: > 5000 сообщений

### 3.2. Метрики Rate (RPS) для API

#### Number of requests (RPS) for internet shop API
**Зачем нужна:**
- Понимание нагрузки на онлайн-магазин
- Прогнозирование пиковых нагрузок
- Планирование масштабирования

**Ярлыки:**
- `method` — HTTP метод (GET, POST, PUT, DELETE)
- `endpoint` — путь запроса (например, "/api/products", "/api/orders")
- `status_code` — код ответа (200, 400, 500)
- `user_type` — тип пользователя (b2c, b2b)

**Пороговые значения:**
- Baseline: среднее значение за последние 7 дней
- Warning: > 150% от baseline
- Critical: > 200% от baseline

#### Number of requests (RPS) for CRM API
**Зачем нужна:**
- Мониторинг активности продавцов
- Понимание нагрузки на CRM
- Выявление аномальной активности

**Ярлыки:**
- `method` — HTTP метод
- `endpoint` — путь запроса
- `status_code` — код ответа
- `user_id` — идентификатор пользователя (для выявления проблемных пользователей)

**Пороговые значения:**
- Baseline: среднее значение за последние 7 дней
- Warning: > 150% от baseline
- Critical: > 200% от baseline

#### Number of requests (RPS) for MES API
**Зачем нужна:**
- Критично для понимания нагрузки на расчёт стоимости
- Выявление пиковых нагрузок после открытия API
- Планирование масштабирования

**Ярлыки:**
- `method` — HTTP метод
- `endpoint` — путь запроса (особенно "/api/calculate-price")
- `status_code` — код ответа
- `source` — источник запроса (internet_shop, crm, external_api)

**Пороговые значения:**
- Baseline: среднее значение за последние 7 дней
- Warning: > 150% от baseline
- Critical: > 200% от baseline

#### Number of requests (RPS) per user для всех API
**Зачем нужна:**
- Выявление злоупотреблений API
- Обнаружение проблемных пользователей
- Защита от DDoS-атак

**Ярлыки:**
- `user_id` — идентификатор пользователя
- `api` — название API (shop, crm, mes)
- `ip_address` — IP-адрес пользователя

**Пороговые значения:**
- Warning: > 100 запросов в секунду от одного пользователя
- Critical: > 500 запросов в секунду от одного пользователя

### 3.3. Метрики использования ресурсов (USE)

#### CPU % для всех API
**Зачем нужна:**
- Понимание загрузки серверов приложений
- Выявление узких мест в производительности
- Планирование масштабирования

**Ярлыки:**
- `instance` — идентификатор инстанса
- `service` — название сервиса (shop_api, crm_api, mes_api)
- `environment` — окружение (dev, release, prod)

**Пороговые значения:**
- Warning: > 70%
- Critical: > 90%

#### Memory Utilisation для всех API и БД
**Зачем нужна:**
- Предотвращение исчерпания памяти
- Выявление утечек памяти
- Планирование масштабирования

**Ярлыки:**
- `instance` — идентификатор инстанса
- `service` — название сервиса
- `environment` — окружение

**Пороговые значения:**
- Warning: > 80%
- Critical: > 90%

#### Number of connections для баз данных
**Зачем нужна:**
- Понимание нагрузки на базы данных
- Предотвращение исчерпания соединений
- Выявление проблем с пулом соединений

**Ярлыки:**
- `database` — название базы данных (shop_db, mes_db)
- `state` — состояние соединения (active, idle, waiting)
- `application` — приложение, использующее соединение

**Пороговые значения:**
- Warning: > 80% от максимального количества соединений
- Critical: > 95% от максимального количества соединений

### 3.4. Метрики производительности (Duration)

#### Response time (latency) для всех API
**Зачем нужна:**
- Понимание производительности API
- Выявление медленных запросов
- Критично для пользовательского опыта

**Ярлыки:**
- `method` — HTTP метод
- `endpoint` — путь запроса
- `status_code` — код ответа
- `percentile` — процентиль (p50, p95, p99)

**Пороговые значения:**
- Warning: p95 > 1 секунда
- Critical: p95 > 3 секунды
- Для MES API расчёт стоимости: Warning > 2 минуты, Critical > 5 минут

### 3.5. Метрики ошибок (Errors)

#### Number of HTTP 200 для всех API
**Зачем нужна:**
- Понимание успешности запросов
- Базовый индикатор здоровья системы
- Используется для расчёта error rate

**Ярлыки:**
- `method` — HTTP метод
- `endpoint` — путь запроса
- `api` — название API

#### Number of HTTP 500 для всех API
**Зачем нужна:**
- Критично для обнаружения ошибок сервера
- Индикатор проблем в приложении
- Используется для расчёта error rate

**Ярлыки:**
- `method` — HTTP метод
- `endpoint` — путь запроса
- `api` — название API
- `error_type` — тип ошибки (exception, timeout, database_error)

**Пороговые значения:**
- Warning: error rate > 1%
- Critical: error rate > 5%

### 3.6. Метрики сессий

#### Number of simultaneous sessions для всех API
**Зачем нужна:**
- Понимание текущей нагрузки на систему
- Выявление пиковых нагрузок
- Планирование масштабирования

**Ярлыки:**
- `api` — название API
- `user_type` — тип пользователя
- `environment` — окружение

**Пороговые значения:**
- Warning: > 80% от максимальной пропускной способности
- Critical: > 95% от максимальной пропускной способности

### 3.7. Метрики трафика

#### Kb transferred (received) и Kb provided (sent) для всех API
**Зачем нужна:**
- Понимание объёма передаваемых данных
- Выявление аномально больших запросов
- Планирование пропускной способности сети

**Ярлыки:**
- `api` — название API
- `endpoint` — путь запроса
- `direction` — направление (in, out)

**Пороговые значения:**
- Warning: > 150% от среднего значения
- Critical: > 200% от среднего значения

### 3.8. Метрики хранилища

#### Size of S3 storage
**Зачем нужна:**
- Контроль использования хранилища 3D-файлов
- Планирование затрат на хранение
- Выявление необходимости очистки старых файлов

**Ярлыки:**
- `bucket` — название bucket (если используется несколько)
- `file_type` — тип файла (3d_model, texture, etc.)

**Пороговые значения:**
- Warning: > 80% от лимита
- Critical: > 95% от лимита

#### Size of shop db instance и MES db instance
**Зачем нужна:**
- Контроль роста баз данных
- Планирование масштабирования
- Предотвращение исчерпания места

**Ярлыки:**
- `database` — название базы данных
- `table` — название таблицы (для детализации)

**Пороговые значения:**
- Warning: > 80% от лимита
- Critical: > 95% от лимита

### 3.9. Дополнительные метрики

## 4. План действий

### Этап 1: Подготовка инфраструктуры (2 недели)

#### 1.1. Развёртывание Prometheus
- **Задача:** Создать инстанс Prometheus на Yandex Cloud (EC2 или Managed Service)
- **Детали:**
  - Использовать Managed Service для Prometheus (если доступен) или развернуть на EC2
  - Настроить persistent storage для метрик (минимум 30 дней хранения)
  - Настроить репликацию для высокой доступности
  - Настроить базовую конфигурацию scrape_configs

#### 1.2. Развёртывание Grafana
- **Задача:** Создать инстанс Grafana для визуализации метрик
- **Детали:**
  - Развернуть на EC2 или использовать Managed Service
  - Настроить подключение к Prometheus
  - Настроить аутентификацию и авторизацию
  - Создать базовые дашборды для каждой команды

#### 1.3. Настройка экспортёров метрик
- **Задача:** Установить и настроить экспортёры для сбора метрик
- **Детали:**
  - **Node Exporter** — для метрик серверов (CPU, память, диск)
  - **PostgreSQL Exporter** — для метрик баз данных
  - **RabbitMQ Exporter** — для метрик очередей
  - **JMX Exporter** — для метрик Java-приложений (Shop API, CRM API)
  - **.NET Exporter** — для метрик C# приложения (MES API)

### Этап 2: Интеграция мониторинга в приложения (3 недели)

#### 2.1. Интеграция в Shop API
- **Задача:** Добавить сбор метрик в Shop API
- **Детали:**
  - Добавить Prometheus client library для Spring Boot
  - Настроить сбор RED-метрик (Rate, Errors, Duration)
  - Добавить кастомные метрики для бизнес-логики
  - Настроить endpoint `/metrics` для Prometheus

#### 2.2. Интеграция в CRM API
- **Задача:** Добавить сбор метрик в CRM API
- **Детали:**
  - Аналогично Shop API
  - Добавить метрики для работы с заказами
  - Настроить метрики для интеграции с RabbitMQ

#### 2.3. Интеграция в MES API
- **Задача:** Добавить сбор метрик в MES API
- **Детали:**
  - Добавить Prometheus client library для .NET
  - Настроить сбор метрик для расчёта стоимости
  - Добавить метрики времени выполнения расчётов
  - Настроить endpoint `/metrics`

### Этап 3: Настройка мониторинга инфраструктуры (2 недели)

#### 3.1. Мониторинг баз данных
- **Задача:** Настроить сбор метрик с PostgreSQL
- **Детали:**
  - Установить PostgreSQL Exporter на серверах БД
  - Настроить сбор метрик: connections, queries, replication lag
  - Настроить метрики размера БД и таблиц
  - Добавить метрики производительности запросов

#### 3.2. Мониторинг RabbitMQ
- **Задача:** Настроить сбор метрик с RabbitMQ
- **Детали:**
  - Установить RabbitMQ Exporter
  - Настроить сбор метрик: queue length, message rate, DLX
  - Настроить метрики для каждой очереди
  - Добавить метрики для consumer'ов

#### 3.3. Мониторинг S3 Storage
- **Задача:** Настроить сбор метрик использования S3
- **Детали:**
  - Использовать CloudWatch метрики (если S3 на AWS) или Yandex Cloud метрики
  - Настроить сбор метрик размера хранилища
  - Добавить метрики количества объектов
  - Настроить алерты при достижении лимитов

### Этап 4: Создание дашбордов (2 недели)

#### 4.1. Дашборд для разработчиков
- **Задача:** Создать дашборды с техническими метриками
- **Детали:**
  - RED-метрики для каждого API
  - Метрики использования ресурсов
  - Метрики ошибок с детализацией
  - Метрики производительности запросов

#### 4.2. Дашборд для DevOps
- **Задача:** Создать дашборды для инфраструктуры
- **Детали:**
  - Метрики серверов (CPU, память, диск)
  - Метрики баз данных
  - Метрики очередей
  - Метрики сети

#### 4.3. Дашборд для бизнеса
- **Задача:** Создать дашборды с бизнес-метриками

## 5. Показатели насыщенности

### Определение насыщенности

Насыщенность (Saturation) — это показатель того, насколько система близка к своей максимальной пропускной способности. Превышение пороговых значений насыщенности означает, что система не справляется с нагрузкой и требуется вмешательство.

### Показатели насыщенности для различных компонентов

#### 5.1. API-сервисы (Shop API, CRM API, MES API)

**Показатель насыщенности:** Длина очереди запросов + время ожидания в очереди

**Пороговые значения:**
- **Warning (70% насыщенности):**
  - Среднее время ожидания в очереди > 500ms
  - Количество запросов в очереди > 100
  - CPU utilization > 70% в течение 5 минут

- **Critical (90% насыщенности):**
  - Среднее время ожидания в очереди > 2 секунды
  - Количество запросов в очереди > 500
  - CPU utilization > 90% в течение 2 минут
  - Error rate > 5%

**Действия при превышении порогов:**

**Warning уровень:**
1. Автоматически: Отправка уведомления в Slack команде разработки
2. Автоматически: Создание тикета в системе отслеживания задач
3. Вручную: Анализ дашбордов для выявления узких мест
4. Вручную: Подготовка к масштабированию (если необходимо)

**Critical уровень:**
1. Автоматически: Отправка критического алерта в Slack и на email
2. Автоматически: Создание критического тикета с высоким приоритетом
3. Автоматически: Уведомление тимлида и продакт-менеджера
4. Автоматически: Активация механизмов ограничения нагрузки (rate limiting)
5. Вручную: Немедленный анализ проблемы командой
6. Вручную: Принятие решения о масштабировании или оптимизации
7. Вручную: При необходимости — временное ограничение функциональности

#### 5.2. Базы данных (Shop DB, MES DB)

**Показатель насыщенности:** Количество активных соединений + время выполнения запросов + длина очереди запросов

**Пороговые значения:**
- **Warning (70% насыщенности):**
  - Количество активных соединений > 70% от максимума
  - Среднее время выполнения запросов > 100ms
  - Количество медленных запросов (> 1 секунды) > 10 в минуту
  - CPU utilization > 70%

- **Critical (90% насыщенности):**
  - Количество активных соединений > 90% от максимума
  - Среднее время выполнения запросов > 500ms
  - Количество медленных запросов > 50 в минуту
  - CPU utilization > 90%
  - Ошибки подключения к БД > 1% от всех запросов

**Действия при превышении порогов:**

**Warning уровень:**
1. Автоматически: Отправка уведомления в Slack команде разработки и DevOps
2. Автоматически: Создание тикета для анализа производительности БД
3. Вручную: Анализ медленных запросов
4. Вручную: Проверка необходимости оптимизации индексов
5. Вручную: Подготовка к созданию read replicas

**Critical уровень:**
1. Автоматически: Отправка критического алерта
2. Автоматически: Создание критического тикета
3. Автоматически: Уведомление тимлида и DBA (если есть)
4. Вручную: Немедленный анализ проблемы
5. Вручную: Принятие решения о:
   - Создании read replicas
   - Оптимизации запросов
   - Масштабировании БД
   - Временном ограничении функциональности

#### 5.3. RabbitMQ

**Показатель насыщенности:** Длина очереди + время обработки сообщений + количество сообщений в DLX

**Пороговые значения:**
- **Warning (70% насыщенности):**
  - Длина очереди > 1000 сообщений
  - Среднее время обработки сообщения > 5 секунд
  - Количество сообщений в DLX > 0
  - Количество сообщений in-flight > 500

- **Critical (90% насыщенности):**
  - Длина очереди > 5000 сообщений
  - Среднее время обработки сообщения > 30 секунд
  - Количество сообщений в DLX > 10
  - Количество сообщений in-flight > 2000
  - Потеря сообщений > 0

**Действия при превышении порогов:**

**Warning уровень:**

2. Автоматически: Создание тикета для анализа очередей
3. Вручную: Анализ причин накопления сообщений
4. Вручную: Проверка производительности consumer'ов
5. Вручную: Подготовка к масштабированию consumer'ов

**Critical уровень:**
1. Автоматически: Отправка критического алерта
2. Автоматически: Создание критического тикета
3. Автоматически: Уведомление тимлида
4. Автоматически: Активация механизмов backpressure
5. Вручную: Немедленный анализ проблемы
6. Вручную: Принятие решения о:
   - Масштабировании consumer'ов
   - Оптимизации обработки сообщений
   - Временном ограничении приёма новых сообщений
   - Ручной обработке критических сообщений из DLX

#### 5.4. MES API (расчёт стоимости)

**Показатель насыщенности:** Количество заказов в очереди на расчёт + среднее время расчёта + количество тайм-аутов

**Пороговые значения:**

  - Среднее время расчёта > 5 минут
  - Количество тайм-аутов > 5% от всех расчётов
  - CPU utilization > 70%

- **Critical (90% насыщенности):**
  - Количество заказов в очереди > 100
  - Среднее время расчёта > 15 минут
  - Количество тайм-аутов > 10% от всех расчётов
  - CPU utilization > 90%
  - Ошибки расчёта > 5%

**Действия при превышении порогов:**

**Warning уровень:**

4. Вручную: Проверка сложности моделей в очереди
5. Вручную: Подготовка к масштабированию worker'ов

**Critical уровень:**
1. Автоматически: Отправка критического алерта
2. Автоматически: Создание критического тикета
3. Автоматически: Уведомление тимлида и продакт-менеджера
4. Автоматически: Уведомление клиентов о возможных задержках (если интегрировано)
5. Вручную: Немедленный анализ проблемы
6. Вручную: Принятие решения о:
   - Масштабировании worker'ов для расчётов
   - Приоритизации расчётов (сначала простые модели)
   - Временном ограничении приёма новых заказов на расчёт
   - Ручной обработке критических заказов

#### 5.5. Хранилище (S3, базы данных)

**Показатель насыщенности:** Процент использования дискового пространства

**Пороговые значения:**

6. Вручную: Временное ограничение загрузки новых файлов (если необходимо)

### Общие принципы реагирования на насыщенность

1. **Проактивность:** Алерты настраиваются на уровне Warning, чтобы успеть принять меры до достижения Critical уровня

2. **Автоматизация:** Критические алерты автоматически создают тикеты и уведомляют ответственных

3. **Эскалация:** При отсутствии реакции на Critical алерт в течение 15 минут происходит эскалация на уровень выше

4. **Документирование:** Все действия при превышении порогов документируются в runbook

5. **Постмортем:** После каждого Critical инцидента проводится анализ и обновление пороговых значений при необходимости

6. **Непрерывное улучшение:** Пороговые значения регулярно пересматриваются на основе исторических данных
